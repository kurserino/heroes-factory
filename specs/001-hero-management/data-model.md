# Phase 1 Data Model: Hero Management

## Entity: Hero

Single entity for this feature. No relationships to other entities.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | UUID (string) | Primary key, generated by persistence layer | Not client-supplied |
| `name` | string | Required, 1–120 chars, trimmed non-empty | Editable |
| `nickname` | string | Required, 1–120 chars, trimmed non-empty | Editable; searched together with `name` |
| `date_of_birth` | date (no time component) | Required, must not be in the future | Editable |
| `universe` | string | Required, 1–120 chars, free text | Editable |
| `main_power` | string | Required, 1–200 chars, free text | Editable |
| `avatar_url` | string (URL) | Required, well-formed URL, MUST resolve to a loadable image (verified server-side per FR-025) | Editable |
| `is_active` | boolean | Required, default `true` on creation | Mutated only via the status-change operation; never set directly through create/edit |
| `created_at` | datetime | Set once at creation, immutable afterward | Drives list ordering (descending) |
| `updated_at` | datetime | Refreshed on every mutation, including activation/deactivation (per clarification session) | |

**API representation**: the JSON representation returned by the API uses exactly these ten
fields (FR-023) — no `deleted_at` or other persisted deletion marker exists.

### Validation rules (enforced server-side, Principle V / FR-022)

- `name`, `nickname`, `universe`, `main_power`: required, non-empty after trimming, within
  length bounds above.
- `date_of_birth`: required, valid calendar date, not in the future.
- `avatar_url`: required, well-formed URL AND must resolve (HTTP fetch, 2xx,
  `Content-Type: image/*`) at submission time — see `research.md` → Avatar URL image
  verification.
- On **create**: `is_active` is always set to `true` by the server; a client-supplied value
  for `is_active`, `id`, `created_at`, or `updated_at` is ignored/rejected.
- On **edit** (`PATCH /heroes/:id`): only `name`, `nickname`, `date_of_birth`, `universe`,
  `main_power`, `avatar_url` are accepted; the target hero MUST currently be active or the
  request is rejected (409/422 — see contracts).
- On **status change** (`PATCH /heroes/:id/status`): only `is_active` is accepted and
  changed; all other fields (including timestamps other than `updated_at`) are left as-is.
- On **delete** (`DELETE /heroes/:id`): the target hero MUST currently be active or the
  request is rejected; on success the row is removed from persistence entirely (no soft
  delete).

### State transitions

```
       create
         │
         ▼
   ┌───────────┐   deactivate (confirm)   ┌────────────┐
   │  ACTIVE   │ ────────────────────────▶ │  INACTIVE  │
   │           │ ◀──────────────────────── │            │
   └───────────┘    activate (confirm)     └────────────┘
         │
         │ delete (confirm)
         ▼
     [removed]
```

- Only an **ACTIVE** hero may transition to **INACTIVE**, be **edited**, or be **deleted**.
- Only an **INACTIVE** hero may transition back to **ACTIVE**.
- **INACTIVE** heroes accept no other operation (edit and delete are rejected server-side
  regardless of what the client sends).
- There is no transition out of "deleted" — it is a terminal removal of the row, not a
  state value.

### Ordering & pagination

- List queries order by `created_at` descending (newest first); ties (identical
  `created_at`) are broken by `id` descending for a stable order (implementation detail
  only — not a business rule).
- Page size is fixed at 10; `page` and `search` (optional) are the only list query
  parameters exposed (see `contracts/heroes-api.md`).
- Search filters by case-insensitive substring match against `name` OR `nickname`, applied
  before pagination.

## Persistence mapping (Prisma / MySQL)

- Table: `heroes`.
- `id`: `CHAR(36)` / Prisma `String @id @default(uuid())`.
- `created_at`, `updated_at`: managed via Prisma `@default(now())` / `@updatedAt`
  respectively, so the persistence layer — not application code — guarantees consistency
  (per plan instruction "creation and update timestamps must be managed consistently by
  the persistence layer").
- `date_of_birth`: `DATE` column (no time component).
- Index: composite/basic index supporting the `created_at DESC` ordering and a
  text-search-friendly index (or plain `LIKE` scan, acceptable at this scale) over `name`/
  `nickname` for the search filter.
